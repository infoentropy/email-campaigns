# CLAUDE.md

This is a **private campaign repo**: email documents and audience definitions for the email tool in [`infoentropy/emails`](https://github.com/infoentropy/emails), which is expected to be cloned next to this repo as `../emails`. If it isn't there, clone it there. Run `git -C ../emails pull` before starting work, so the tool and its docs are current.

**Before touching anything, read `../emails/docs/agents.md`.** It's the guide for editing documents, settling audiences into facets, and converting audience markers for Iterable. Don't read the tool's specs unless you're changing the tool.

## Layout

- `campaigns/*.json`: one email document each. The person may have one open in the editor (file sync), so re-read a file before each change and write it in one go.
- `iterable/fields.md`: the Iterable user fields. A person writes it. Write facet conditions only from what it says, and ask when it doesn't say.
- `iterable/facets.json`: the approved facet library. Change it only with the person's explicit approval, following the settling procedure in `agents.md`.
- `out/`: built HTML, **generated by CI, not by hand**: `<name>.html` (email, audience markers), `iterable/<name>.html` (paste into Iterable; other platforms get their own `out/<platform>/` dir), `.manifest.json` (build state), `index.html` (links to every build). Don't edit these or commit builds yourself; see Workflow.
- `scripts/build.mjs`: the build. `.github/workflows/build.yml`: runs it.

## Workflow

1. **Author.** Draft or edit `campaigns/<date>-<slug>.json` on a branch and run `check.js` until it returns `[]` (`ruleset_unsettled` warnings are fine while drafting). Settle rulesets into facets with the person (see Rules). Don't build `out/` and don't touch `out/index.html`.
2. **Pull request.** The `Build emails` check runs `scripts/build.mjs` in CI without committing. It fails on check errors, unsettled rulesets, and facets that are missing or not approved, so a campaign can't merge until its audiences are settled. Fix the failure in the document or facets, never by editing `out/`.
3. **Merge to `main`.** CI builds every pending campaign and commits `out/` back as `email-build[bot]` (`[skip ci]`). Pull before further work, since `main` gets that extra commit.
4. **Hand off.** Tell the person where the Iterable file will be (`out/iterable/<name>.html`) and which facets it uses (the build log lists them). They paste it into Iterable.

**What "pending" means.** `out/.manifest.json` stores, per campaign, a hash of its document, a hash of `iterable/facets.json` and the `emails` tool commit. A campaign is pending when an output file is missing or any of these changed, so edits, facet changes and tool updates all rebuild. A second run finds nothing pending; that's the done-or-not state, with no status flags. Builds on `main` queue one at a time.

To see what is pending, or to reproduce a CI failure, run `node scripts/build.mjs --check` (no writes; exit 1 if anything is pending or fails) or `node scripts/build.mjs` (builds into `out/`; don't commit that on a feature branch, since CI does it on `main`). Both read the tool from `../emails`, or from `EMAILS_DIR`. CI needs the `EMAILS_REPO_TOKEN` secret if `infoentropy/emails` is private.

## How the pieces fit

- A document is `{version, name, subject, preheader, theme, nextId, blocks[]}`. Blocks hold content only (styling comes from `theme`). Audience is per block: `ruleset` (free text while drafting, then facet ids joined with ` + `, e.g. `region.us-ca-gb + subscription.not-paying`), `switch` (adjacent blocks sharing a value; first matching case wins, a last case with no `ruleset` is the fallback) and `hidden`. New block id is `"b" + nextId`, then bump `nextId`; ids are never reused.
- `iterable/facets.json` is keyed `category → name` (facet id `category.name`). Each facet has `description`, `fields` (must be fields in `iterable/fields.md`), an Iterable `condition`, `approved` date and `examples`. When `fields.md` changes, re-check every facet whose `fields` include the changed field.
- `check.js` warns `ruleset_unsettled` for free-text rulesets; that's normal while drafting.
- Don't read rendered HTML to judge a change; rely on `check.js` and leave visual judgement to the person. `README.md` describes how to turn this example repo into a real private one.

## Commands

```sh
node ../emails/render/check.js campaigns/<file>.json                  # issues as JSON; [] = good
node scripts/build.mjs --check                                        # what CI would build; exit 1 if pending or failing
node ../emails/render/preview.js campaigns/<file>.json --as <facet> > out/<name>.preview.html   # milestones only
```

## Rules

- Never commit secrets. An Iterable API key, if one is used, comes from the environment (e.g. `ITERABLE_API_KEY`).
- Never settle a ruleset, add a facet or approve one without the person.
- Iterable syntax is written only by `scripts/build.mjs` (from `iterable/facets.json`) when it converts markers into `out/iterable/<name>.html`, never into documents.
- Pushing to Iterable through its API isn't set up yet. Hand the person the `out/iterable/<name>.html` file to paste into Iterable, and say which facets it uses.
- Don't commit generated files in `out/` (builds, manifest, index entries for builds); CI does. If the build can't handle a case, fix `scripts/build.mjs` rather than hand-writing output.
- Previews are the one thing you add to `out/` yourself, at milestones. When you do, add an `<li>` for it to that campaign's section in `out/index.html` in the same commit: a relative `href` (just the file name) and a short `<small>` note (e.g. "preview as `region.us`"), after the email and Iterable links. Check links with `grep -o 'href="[^"]*"' out/index.html` and confirm each file exists. The build adds a section for each new campaign.
